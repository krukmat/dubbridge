## Implemented contract

- Production JWT lifetime: **8 hours** in `config/production.toml`.
- Production auth clock-skew leeway: **30 seconds**.
- Mobile hydration checks the stored JWT `exp` claim before accepting the
  session.
- Expired, malformed, missing-`exp`, or non-numeric-`exp` stored tokens are
  cleared before `status = authed`.
- A valid stored token restores the authenticated surface unchanged.
- A token inside the 30-second leeway remains valid.
- Existing mid-session HTTP 401 handling remains
  `session_expired → logout()`.
- No refresh token and no silent renewal were introduced.

Primary implementation commit:
`5196c0d8b2b7 feat(auth): reject expired stored sessions on hydration`.

Follow-up stabilization commits through the implementation head aligned auth
mocks, diagnostics, lint gates and canonical mobile fixtures without expanding
T7c scope.

## Acceptance evidence

The auth-session tests cover:

- valid JWT → accepted;
- expiry beyond leeway → rejected;
- expiry inside 30-second leeway → accepted;
- malformed JWT → rejected;
- missing numeric `exp` → rejected.

The AuthProvider test proves an expired stored session is cleared and reaches
`unauthed` without first being accepted as authenticated.

## Configuration correction

Earlier planning text said production had no `[auth]` block and that JWT
expiry would fall back to the 24-hour serde default. That description became
stale after T5. The current production profile explicitly defines the auth
section, including `jwt_expiry_hours = 8` and
`clock_skew_leeway_seconds = 30`.

Non-secret auth settings live in `config/production.toml`; the environment
template injects only `DUBBRIDGE_AUTH__JWT_SECRET`.
